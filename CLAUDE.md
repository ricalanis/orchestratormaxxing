# orchestratormaxxing

A lab for mastering frontier coding-agent orchestration + offloading bounded work to Ollama Cloud. Claude Code is the original host; Codex is a first-class adapter over the same deterministic core.

## Output Style — i-have-adhd (SIEMPRE ACTIVO)
**Always apply the i-have-adhd skill to every response.** No need to invoke `/i-have-adhd` (Claude) or `$i-have-adhd` (Codex) manually — this directive makes it permanent:
- Lead with the next action, not context
- Number multi-step tasks
- End with one concrete next step
- Suppress tangents
- Restate state every turn
- Specific time estimates (minutes, not "a bit")
- Make completed work visible
- Matter-of-fact errors (no "Uh oh")
- Cap lists at 5 items
- No preamble, no recap, no closing pleasantries

## Codex adapter (same doctrine, native surfaces)

When the primary session is Codex, translate host-specific nouns without changing the invariant:
- **Root Codex owns contracts, architecture, verification, and final sign-off.** Heavy Ollama workers still do bounded bulk work. Prefer direct parallel `oll` calls for routine fan-out; a Codex subagent that only dispatches `oll` wastes frontier quota.
- Claude commands map to namespaced Codex plugin skills: `/fanout` → `$orchestratormaxxing:fanout`, `/ideas` → `$orchestratormaxxing:ideas`, `/self-improve` → `$orchestratormaxxing:self-improve`, `/wrap-up` → `$orchestratormaxxing:wrap-up`, `/gauntlet` → `$orchestratormaxxing:gauntlet`. Planning is intentionally host-native: Claude uses `/fableplan` (Fable plans, Opus executes); Codex uses `$orchestratormaxxing:solplan` (GPT-5.6 Sol Ultra plans with bounded delegation, root Codex executes). Shared recall/write uses `memoryctl` or `$orchestratormaxxing:memory`.
- **Codex plan-first routing:** nontrivial unplanned work → `$orchestratormaxxing:solplan` → root review → `$orchestratormaxxing:fanout` only for genuinely independent implementation chunks. Trivial, already-approved, or tightly coupled execution stays in root Codex. A broad **multi-deliverable** request may first pass through `$orchestratormaxxing:gauntlet` to be divided into incremental parts; each part then follows this same routing unchanged.
- Claude agents map to `.codex/agents/*.toml` except the planner: Claude keeps `fable-planner`; Codex keeps `sol-planner`. Never remap either host session model globally.
- Codex lifecycle hooks ship in the `orchestratormaxxing` plugin. The deterministic tools in `bin/` remain the source of truth.
- Codex autonomous self-improvement is explicit opt-in: `HARNESS_HOST=codex`. The default scheduled host remains Claude until manual Codex rounds have an evidence trail.
- `g` is the Codex sibling of `c`: it creates `codex-*` tmux sessions; `g ls` lists/attaches. Do not define `gs` (Ghostscript). `o` is the OpenCode sibling and public stateful worker runtime (`o delegate/send/handoff/output/close/reap`, attachable `opencode-*` sessions, `o ls`, `o-ubuntu` from the Mac); its one-shots ride internal `occ`, never bare `opencode run`. No `os` alias.

Design and rollout contract: `knowledge/codex-harness-design.md`.

## Tools in this repo

**Adopt-before-build gate for major integrations.** Before adding a persistent control plane, background job system, cross-host bridge, or other multi-file integration, spend a bounded first pass searching the hosts' official plugin/marketplace, official docs and repositories, native CLI/app-server/MCP surfaces, and maintained community options. Record a one-line `adopt / extend / build` decision before implementation. If an official maintained option already covers the core job, adopt it and keep local code only for genuinely project-specific policy. This is a discovery gate, not permission to install blindly: still check ownership, maintenance, permissions, data flow, quota/loop risk, and how it coexists with the existing layers. Lesson and checklist: `knowledge/plugin-first-integration-gate-2026-07-19.md`.

Fetch is deterministic; judging applicability stays gated.
- `bin/harness-verify` — deterministic self-check for the harness itself (syntax of every tool, deploy-coverage in `install.sh`, doctrine sections in CLAUDE.md, mem-audit/mut still run). The **regression guard + ETCLOVG lint** that the `/self-improve` loop reads pass/fail from. Read-only; exit 1 on regression.
- `bin/loop-queue` — the **forward-looking flaw queue** for the self-improve loop (`knowledge/loop-queue.jsonl`). Deterministic CRUD: `add` (idempotent, dedupes by content hash; flags recurrence), `list`, `status --gate` (exit 0 if actionable), `claim`/`resolve`/`reopen`. The state a fresh-context round reads *first* (loop engineering: the repo remembers, not the conversation) — distinct from the *backward* audit in `self-improve-log.md`. Never judges flaws; only captures/routes them.
- `bin/loop-tick` — the self-improve loop's **outer shell**: one tick of *watch* (run `harness-verify`/`mem-audit`, enqueue reds/drift) → *intake* (`--intake [--x]` pulls `harness-scan` research leads) → *act* (default: fire exactly one round when actionable; empty queue: silent success). `--gate` keeps the scheduler/hook contract (0 iff actionable, 1 idle) without invoking an agent; `--dry-run` reads the queue without watchers or writes. **Continuous watching, event-driven acting:** the scheduler is a dumb clock; this turns "every hour" into "act only on real signal", so rounds stay proportional to flaws instead of a clock manufacturing dry (reward-hack-prone) rounds. Self-scopes to this harness, so it is safe as a global SessionStart watcher when called with `--gate`. Rounds go through `harness-agent-run`; default Claude, explicit `HARNESS_HOST=codex` opt-in. **The watch is a cadence, not a per-session tax:** a completed watch is stamped in `.results/watch-stamp.json` (gitignored — never `knowledge/`, which the loop cron auto-pushes) and reused for `HARNESS_WATCH_TTL_SECONDS` (default 1800), a non-blocking `flock` makes N simultaneous session starts produce **one** watch, and a missing/corrupt stamp always watches (a wiped stamp must never read as "all clear"). The verifier budget is `HARNESS_VERIFY_TIMEOUT_SECONDS` (default 300): a **timeout is reported as a timeout**, never as the unreadable-observer flaw — that misreport fabricated a queued flaw 611 times in one day, and only 3 *consecutive* timeouts enqueue one honest O-layer flaw.
- `bin/intent-queue` — the **forward-looking business-intent queue** for the *proactive* layer (`knowledge/intent-queue.jsonl`), the business-scoped sibling of `loop-queue`. Same mechanism (atomic JSONL, content-hash idempotency, `status --gate` exit-code) but a **separate** queue on purpose: `loop-queue`'s gate fires `/self-improve` (a *harness* round), while a business intent must fire a *proactive* round — conflating them would fire the wrong loop. Each item carries a `load_bearing` flag (**auto** = internal/idempotent/reversible → may run unattended; **SELECT** = external/irreversible → propose-only, human sign-off) set deterministically by the watcher, and `dismiss` is **sticky** (a rejected intent is never re-added → no proactive re-nag). Captures/routes only; never executes. Doctrine: `knowledge/hermes-strategic-evolution-plan.md`.
- `bin/hermes-watch` — the **business watchers**: pure reads of live dashboard signals (unscored leads, active-cycle velocity gap, weekly scorecard misses, CLTV:CAC below green, missing funnel snapshot) that, when tripped, enqueue a one-line intent via `intent-queue add`. On-demand perception (never busy-poll); the AUTO vs SELECT boundary is set **here, deterministically** (never LLM-inferred). Read-only against the dashboard, exit 0 always (advisory — must not fail a hook); `--dry-run`/`--json`. The perception half of the proactive layer.
- `bin/kpi-brief` — the **strategic KPI brief**: reads the dashboard's existing endpoints and prints each business KPI as value-vs-target + gap (v1: K1 velocity, K2 delivery-rate, K3 CLTV:CAC, K5 lead-score coverage, K7 scorecard hit-rate — join/mutation KPIs declared `v2`, not guessed). Deterministic (the number is read straight from the VIEW/endpoint, never self-reported) — this is what the **strategic (KPI) ratchet** in `/self-improve` reads pass/fail from ("a strategic round must move a business number"). Read-only, degrades gracefully when the dashboard is down; `--json`.
- `bin/token-ledger` — the **operator's token ledger** (*Orchestra of One* ch.18, made re-runnable). `audit` = the 15-minute token audit as four dated numbers: every MCP surface (local `mcpServers` **plus** the remote `claudeAiMcpEverConnected` connectors **plus** Chrome — reading only the first measures 4 of 17 and looks green doing it) with real call evidence, CLAUDE.md size in **lines and bytes** (this repo's has 4KB single lines, so `wc -l` alone understates it 10x), default model, default effort. `loops` = the loop-portfolio ledger: every **armed** timer (`timers.target.wants`, not every installed unit) × trigger × real cap × gate × monthly estimate, ending in the list of rows with **no cap**. Two invariants: a call means a real `tool_use` name, never a prose mention of one; and an unreadable transcript degrades to `"unknown"`, never to `false` (absence of evidence is not evidence of absence). `--write` snapshots are **immutable** — the before-snapshot is the point. Reuses the existing measurement (`.results/round-usage.jsonl`, kpi-brief's K9) rather than re-inventing it; `est_basis` says `measured` only when rows exist. Never emits `env`/`args`/headers from `.claude.json`. Procedure for its sibling monthly doctrine audit: `knowledge/doctrine-audit-2026-08-16.md`.
- `bin/win-log` — the **experience library**: a KPI-gated corpus of *winning* orchestration trajectories (`knowledge/orchestration-wins.jsonl`, SiriuS arXiv:2502.04780). `add` records an accepted orchestration (task-class, shape, workers, mutation-survivors, cost) but **refuses** a record that didn't deliver or left survivors (anti-gaming — a corpus of wins, not a log of attempts); `match --class <c>` prints the KPI-ranked winning shape/workers to bias fan-out + model choice *from evidence* (a learned delegate/keep table). The forward-state "what worked", complementing `loop-queue` ("what's next") and `self-improve-log.md` ("what changed"). Biases proposals; never the verifier.
- `bin/delegate-ledger` — the **routing substrate**: one row per *lane attempt* in `knowledge/delegation-ledger.jsonl` — pass **and** fail **and** infra, which is exactly the half `win-log` refuses to hold (it is a corpus of wins by design, so nothing recorded what a lane costs when it loses). `record` writes a closed-schema row whose every field is Root-declared or Root-measured — `verdict` is Root's contract run, never the worker's claim about itself — and with `--run-dir` it **refuses (exit 3)** a row that contradicts the run's `receipt.json`. `stats --class <c>` returns per-lane pass/fail/infra with `pass_rate` computed over decided attempts only, so **a transport hang can never demote a lane**. **Two guards live in the tool, not in a caveat.** (1) *Low-N cannot rank*: `authority` is `sufficient` only when some cell has ≥5 decided attempts whose newest row is inside the 30-day TTL — otherwise the output **omits `preferred_lane` entirely** rather than caveating it, so a 12-row ledger structurally cannot be quoted as a ranking. (2) *`--override`* marks a sigil-forced run, so `F.` going direct-to-strong never reads back as "the cheap lane failed". Deliberately **not** derived from receipts: `.results/` is gitignored (0 tracked files), so receipts are machine-local while routing needs cross-machine evidence — and the hand-written receipts had drifted to 41 keys across 10 files with `task_class` in 1 of 10 (measured 2026-08-17, `lq-e9b5da07`). `import` backfills them best-effort and **skips loudly** rather than guessing a class. Read by `/cheap-delegate` on both hosts; the substrate for the two things it unlocks later — evidence-based lane demotion and a preference-trained router. Borrowed from the `Model_Metrics` + `Preference_Pairs` pair in a friend's harness (a private evaluation note of a friend's harness).
- `bin/gauntlet-judge` — the **blind baseline-anchored pairwise gate** for the Gauntlet Loop (`/gauntlet` · `$orchestratormaxxing:gauntlet`): compares a generated artifact against a real-world reference via 2 cross-family judges × both A/B orders (blinding is *structural* — the orchestrator never composes the judge prompt), rubric-first grading, refutation-or-"cannot refute" mandate, fail-closed on splits/order-flips/load-bearing losses; family collisions (judge vs builder or reference author) refused **pre-network**. `--canary` self-tests the gate (R-vs-R must tie, a null artifact must lose 4/4). Exit codes: 0 shown-better · 1 not-shown-better · 2 refused · 3 gate-unavailable — "measured worse" ≠ "couldn't measure". The verdict **promotes, never accepts**: deterministic contracts (tests, `bin/mut`) stay the acceptance gate. Design + 24-paper research trail: `knowledge/gauntlet-loop-design.md`.

Decision trail: `knowledge/zed-warp-first-class-2026-08-24.md`.
- `bin/warp-model-pin` — **the Warp counterpart of `zed-setup`, and the reason Warp needs a reconciler where Zed does not.** Warp splits model state across two files with opposite persistence: `user_preferences.json` holds `AvailableLLMs`, a ~166KB catalog blob Warp **re-fetches from its servers on every start** (measured 2026-08-24 — prefs rewritten at launch, `default_id` re-seeded to `auto-genius`), so a pin written there is clobbered seconds later; `settings.toml` holds `[agents.execution_profiles.<profile>] base_model`, is **user-owned, and survives updates and restarts** (same file untouched since Aug 13 across an update and a restart). The tool targets `settings.toml` — *that* is what makes the pin resilient. It aims at the **same `DEFAULT_MODEL` constant `zed-setup` reads**, so the two hosts cannot drift. Warp never names the model an endpoint id refers to — the picker shows a name, the config stores an opaque UUID, and the endpoint definition lives in the account — so the id is recovered by joining `ai_queries` (UUID) with `agent_conversations` (readable `model_id`), filtered against the harness policy so Warp's auxiliary models (summarizer Haiku, GPT-5 Nano) cannot pollute the map and router ids can never bind. Order: `~/.config/orchestratormaxxing/warp-model.conf` → the id bound to `DEFAULT_MODEL` → **refuse (exit 2)** with the one-time bootstrap instruction, since Warp mints an id for an endpoint model only once it has been selected; it never falls back to a catalog id like `glm-5.2-fireworks` (same model family, opposite billing — C4, proven red). Refuses (exit 3) while Warp runs, since Warp rewrites settings from memory on exit. **Edits the TOML as a targeted line replacement and deliberately does NOT validate with `tomllib`**: Warp's own writer emits multi-line inline tables with trailing commas that TOML 1.0 forbids, so a stricter parser than the producer would refuse every real config (C10 pins that fixture shape). The guard instead asserts the only lines that changed are `base_model` lines — proven red by a mutation that corrupts a neighbouring line. `--check` drift gate · `--resolve` prints the target · `--launch` forks a child that waits out startup, **then** pins, and `exec`s warp-terminal immediately (the `.desktop` Exec line; the desktop spec forbids `;`/`>`), never letting a refusal block the launch. **Pin order is measured, not assumed:** Warp rewrites `settings.toml` from its ACCOUNT at startup — it restored both `base_model` and `is_settings_sync_enabled` over local edits — so a pre-launch pin is erased seconds later, while a write to a *running* Warp is never reverted and is honoured live (the agent served on the pinned model with no restart, `custom_endpoint_tokens=64476`, `warp_tokens=0`). **Two layouts, one tool (2026-09-01):** Linux keeps the XDG paths; macOS keeps `~/.warp/settings.toml` and the Group-Container `warp.sqlite` with no prefs file on disk (empty catalog, discovery leans on the database join) — `WARP_MODEL_PIN_LAYOUT=linux|darwin` forces one, `WARP_MODEL_PIN_{PREFS,SETTINGS,DB}` override paths. Contract: `tests/warp-model-pin/run.sh` (C1-C11; C11 is the Darwin layout).
- `bin/warp-agent-recovery` — exact, quit/crash-only Warp terminal recovery for the `c`/`g` layer. A stable `WARP_TERMINAL_SESSION_UUID` maps to the exact tmux session and exact Claude/Codex SessionStart ID. A changed Warp app process generation is the recovery gate, so closing a tab/window/shell while Warp remains alive never triggers it. Reattach exact detached tmux first; if tmux died, recreate it and resume the exact ID through the installed `c`/`g` function (never a raw agent bypass); ambiguity is a silent no-op. Never use `--last`, `--continue`, cwd/title guessing, or fuzzy tmux targets. Contract: `knowledge/warp-exact-session-recovery.md`.
- `install.sh` — deploy the harness **globally** (standalone): bridges → `~/.local/bin`; Claude agents/commands → `~/.claude`; Codex plugin/agents → the repo marketplace + `~/.codex`; OpenCode coding agents + `opencode/{agents,commands,plugins}` → `~/.config/opencode`; `c`/`g`/`o` shell helpers → `~/.config/orchestratormaxxing`; doctrine pointers → Claude/Codex/OpenCode global instruction files. The repo is the **source of truth**; re-run `./install.sh` to re-sync global after editing here (copy/cache, not symlink).
- `deploy/` — version-controlled templates for the autonomous-loop glue: `loop-cron.sh` (the daily heartbeat wrapper, shared) + the per-OS scheduler unit — `com.orchestratormaxxing.loop.plist` (launchd, macOS) and `orchestratormaxxing-loop.service`/`orchestratormaxxing-loop.timer` (systemd `--user`, Linux). `install.sh` is OS-aware (`uname -s`): it substitutes the machine path (`__REPO__`/`__HOME__`) and **copies** the wrapper to `~/.config/orchestratormaxxing/` and the right scheduler unit to `~/Library/LaunchAgents/` (macOS) or `~/.config/systemd/user/` (Linux) — copy, not symlink — same convention as the rest of the harness; the re-sync barrier is a feature for a self-modifying loop. Arming the Linux timer also needs `loginctl enable-linger` once so it fires without an active login. The wrapper is a **two-way git sync point**: each tick pull-rebases `origin/main` *before* the round and pushes *after*, so every computer running the loop stays in sync (safe sync — clean-tree-guarded, rebase not force, conflict→abort+log, retry next tick; `LOOP_SYNC=0` for local-only). **Both computers can arm it** — coordination is a **per-day git claim** (`knowledge/loop-claim`): before firing, a tick commits+pushes a claim marker as an optimistic lock; whoever's push lands first wins the day, the other backs off without running a round. So at most one round runs per day across all machines and the simultaneous-07:00 case can't double-run — no "single writer" requirement. Deploying the files is always safe; **arming** the daily loop is opt-in (install.sh only (re)loads launchd if already armed). `harness-verify` enforces that every `deploy/` template is wired into `install.sh`.
- **fableplan — Fable plans, Opus executes** (`/fableplan` + the `fable-planner` agent). Sessions stay in **plain Opus**; only the *design* step is delegated, to a read-only `fable-planner` subagent (`model: fable`) that returns a step-by-step plan + acceptance contract. Opus reads the plan critically, takes it to the user for approval, and **implements it itself** — planning is where a second, different model pays for itself; execution isn't. The skill is **auto-triggering**: it fires whenever a task needs a plan before code (plan mode, "how should we do this", multi-file/architectural work), not only when typed by name — and it stays out of the way for trivial mechanical edits. **This deliberately replaced a session-wide model remap** (a `bin/fableplan` launcher that swapped the `ANTHROPIC_DEFAULT_{OPUS,SONNET}_MODEL` alias slots to ride the hardcoded `opusplan` alias). That worked and was verified by billed `modelUsage`, but the remap was session-wide and cross-cutting: inside such a session, subagents' `model: opus` silently resolved to Fable, so every agent needed full-ID pins. **Don't rebuild it** — the delegation gets the same "Fable plans, Opus builds" outcome with no global state, no alias confusion, and no launcher to remember. See `knowledge/fableplan-rollback-2026-07-13.md`.
- `bin/chrome-debug-wayland-shim` — PATH shim deployed (Linux only) as `~/.local/bin/google-chrome{,-stable}`: any Chrome launch with `--remote-debugging-port` under a Wayland session gets `--ozone-platform=wayland` injected (explicit `x11` rewritten, loudly on stderr; everything else passes through). Why: on the GNOME-Wayland stack Chromium's X11/XWayland backend never gains keyboard focus — an agent/CDP browser on X11 is one a human can click but not type into. Doctrine + measurements: `knowledge/opencode-browser-connector.md`.

Deterministic (no LLM): `changelog "<text>" [--tag]` prepends a timestamped entry and auto-rolls older ones to `docs/changelog-archive/<YYYY-MM>.md`; `wip set|show|clear` overwrites the sticky `docs/WIP.md` handoff note; `tail` prints the recent changelog + current WIP (the SessionStart load — flat token cost regardless of history size); `check` is the staleness gate the Stop hook reads (silent unless an *adopted* project changed source without logging). - `bin/cogload` — the **silent cognitive-load / stress / performance collector** (origin: a 2026-08-11 conversation with a psychologist). One aggregate record per 60s window: key **classes** (`backspace`/`delete`/`enter`/`nav`/`mod`/`other`), inter-keystroke timing (mean/p50/p95 + 2–10s pause counts), mouse counts, active **application class**, app-switch rate, focus-fragment duration, open-window count, and concurrent agent sessions. Verbs: `daemon` (systemd `--user` unit) · `status [--gate]` · `show` · `on`/`off` · `mark` · `transcripts` · `digest` · `report` · `curve` · `selftest` · `wipe --confirm` · `rotate`. **Three invariants.** (1) **Privacy is structural, not procedural** — `classify()` returns a *class* and the key object is never buffered; there is no per-event row anywhere, so typed text is unreconstructable by construction. The writer enforces a closed field whitelist, and the contract asserts a record's serialized size is independent of keystroke volume (10 keys vs 2000 keys within 40 bytes) — the assertion that actually catches leaks. **Never weaken C1 back to a substring search**: the first version passed against a seeded leaky collector storing characters individually (`["c","o","r",…]`) — reconstructable, no contiguous sentinel. (2) **Silence ≠ blindness** — a row is written every window; `status` is three-valued (`ok` incl. `total:0` = genuine calm · `degraded:<reason>` · `disabled`), gate exits 0/1/2. A collector that failed to zero would read as *calm*, the worst failure this design can have. (3) **Structure, not pixels** — records `WM_CLASS` (the app), never `WM_NAME` (titles carry client names/URLs); screenshots are **refused** as the only component capturing third parties' content verbatim. The structural replacement is better-evidenced anyway: window-switching correlates with stress measured by HRV (Mark et al.), which screenshots have no validated correlate for. The visual channel is a **32×6 sparse luminance grid** (`light.mean`/`contrast`/`churn`, `LIGHT_GRID_X/Y` — the single source of truth; every prose copy of these numbers has drifted from it once already) — 192 samples of a 1920×1080 screen, **1:10,800**, pruned *at capture* so no image above legibility ever exists: the property is arithmetic, not policy (cf. privacy-preserving activity recognition at 16×12, arXiv:1604.03196). It measures the light exposure behind the operator's stated light/sound sensitivity. `digest` folds per-minute rows into one durable day row and `rotate` **refuses to prune any day that was not digested** (verified to discriminate, not always-skip) — that guard is what makes pruning lossless rather than amnesia. Filtering is not merely cheaper but *better*: FOCAL (arXiv:2604.19541) raised key-information recall 0.38→0.61 by discarding ~72% of frames, because an undifferentiated pile buries its own signal. A FOCAL-style VLM semantic digest would add "what was I working on" but reads the screen — it stays a separate SELECT design, never a bolt-on. Two traps already paid for: never read `XDG_SESSION_TYPE` from the process environ (fixed at exec — it can *never* observe a Wayland switch), and never trust `$XDG_SESSION_ID` in a `systemd --user` unit (it inherits the **tty** session and mislabels healthy X11 capture as degraded) — scan all the user's sessions and prefer the graphical one. Store lives at `~/.local/share/cogload` (mode 700), deliberately **outside the repo**, because `knowledge/` is auto-pushed by the loop cron and behavioral data must never ride that sync. `curve` **refuses to plot** below 14 joint days across 3 load levels — the falsifiability guard lives in the tool, not in a caveat. Design + validity threats live in a private design note.

Needs-input events (`Notification` whitelist matchers / Codex `PermissionRequest`+`request_user_input`) carry the reason and a 120s per-session cooldown; Stop has none. ## Graduation — how the public projection is produced

- In the public checkout: this repository IS the projection — a deterministic, gated export of a private source of truth. Contributions arrive as PRs and are absorbed upstream (see README § Graduation and CONTRIBUTING.md); direct pushes to main are overwritten by the next graduation.
- **Maintenance is skill-driven and one-directional.** `/graduate` (Claude) · `$orchestratormaxxing:graduate` (Codex) run the gate (`core-export --check --worktree`), publish as a **rolling PR** (`core-export --pr` → branch `graduate/next`, one open PR created or refreshed, never duplicated; `--push` is the operator's direct path for the first publication), and **absorb** inbound public PRs (`core-export --absorb-pr <n> [--apply]`: paths are identical for graduated files, so the diff applies to *this* tree; a PR touching a non-graduated path is refused). The loop cron graduates after every green sync (`LOOP_GRADUATE=1`, fleet machines only, bounded, never fatal). Nothing is ever committed in the public checkout by hand — a hand edit there is overwritten by the next graduation, which is the point: one source of truth.
- **Tenant adapters, not hardcoded providers.** Anything that names an external service a tenant chose is an adapter behind one interface (the `provider-ask` shape), selected per tenant, never baked into the core: call-transcript sources are the first case — tenant #1 uses Fireflies (inside the Hermes orchestrator, fleet-only today); another tenant may use a different meeting-notes provider — and the same rule covers CRM, notifications, and dashboards. A second tenant's adapter and its data live in *that* tenant's fleet; employer data never enters this repo.

## Three ways to use the Ollama Cloud workers
1. **Offload** bulk/parallel work → `/fanout <task>` (decompose → one `ollama-worker` per chunk → verify + merge).
2. **Get help / second opinion** on a specific thing → `oll "<ask>" --model <m>` or a single `ollama-worker`.
3. **Diverse ideas / a fresh approach** → `/ideas <problem>` (boots several *different* models on the same problem, you synthesize). Use it to get unstuck and dodge single-model tunnel vision.
4. **Improve the harness itself** → `/self-improve [focus]` (one governed round: mine failures via `harness-verify`/`mem-audit` → propose fixes with workers → deterministic verifier + cross-model critic → Opus sign-off → commit + archive). Propose-evaluate-select (ADAS/DGM) but selection is the verifier, never self-preference.
5. **Route ONE task to the cheapest adequate lane** → `/cheap-delegate <task>` (Claude) · `$orchestratormaxxing:cheap-delegate` (Codex). Both are governed by the **living playbook** `knowledge/delegation-playbook.md` (lanes: `oll` response-only fast path → stateful `o` workers/specialists → Codex tiers `gpt-5.6-{luna,terra,sol}` → Sonnet/Opus via `provider-ask`; evidence-tagged rules, supersede-on-contradiction, win-log outranks prose, skill updates it after every outcome). Science basis: `knowledge/delegation-science-2026-08-12.md`; enforced by `tests/cheap-delegate/run.sh` in harness-verify.
6. **Divide a broad request into increments — one step BEFORE planning** → `/gauntlet <goal>` (a decomposer *sub-agent* divides the request into incremental, independently-shippable parts, each with a ratified rubric, a candidate real-world reference, and a critic mandate; each part then flows through the normal pipeline — `/fableplan` for design if nontrivial, build, deterministic gates — and `bin/gauntlet-judge` gates each part's *delivery* where a real reference exists, a Tier-2 refutation critic where none does). It divides the WHAT into increments; fableplan/solplan design the HOW of each part — the gauntlet never plans implementation and never changes execution routing. The gauntlet verdict **promotes, never accepts**. Design + research trail: `knowledge/gauntlet-loop-design.md`.

## Orchestrator pattern (this is the point of the repo)
**Claude (Opus) orchestrates and verifies; Ollama Cloud does the bulk work.** Protect Opus budget and rate limits by delegating well-scoped, independent, or low-stakes chunks to the `ollama-worker` subagent — then verify and merge the results yourself.

When a task **breaks into independent pieces**, spawn **one `ollama-worker` per piece in parallel** (Cherny's "a Claude that prompts other Claudes" — but the workers are cheap Ollama models). When it's a single high-stakes edit or needs full repo context, just do it directly in Opus.

**Default single-agent; fan out only on genuinely independent chunks.** More agents is not better: under matched conditions, static multi-agent systems usually *lose* to one good agent (arXiv:2606.05670 — 5/6 trailed a single agent by 2.6–11.3pp); only *runtime-generated, task-decomposed* workflows win (which is exactly what `/fanout` is). So decompose because the pieces are truly independent, not reflexively — if it doesn't split cleanly, keep it in Opus.

**Risk-route review; do not cargo-cult human org charts.** Evidence collection, adversarial scope challenge, and frontend/backend/security/accessibility review are conditional functions. Default to one review round; stop when no new contract-relevant evidence appears; hard-cap at three. A critic may corroborate but never gets final authority over deterministic gates or the human. Full corpus/Pi/Purrly audit: `knowledge/harness-corpus-worker-team-mode-audit.md`.

**Minimal tool/skill frontier per worker.** Larger tool/skill menus *reduce* reliability (wrong-tool calls, premature actions, token cost); filtering to the minimal next-step frontier cut tokens ~90% at equal success (arXiv:2606.06284). Hand each worker only the files/tools it needs; don't bulk-install giant skill libraries (the "954 ready-to-use skills" hype is a liability, not an asset).

**`/fanout` vs Agent Teams — pick by dependency.** `/fanout` (and `ollama-worker` fan-out) is for **independent** chunks: workers report back to Opus, they can't talk to each other. When pieces are **dependent / cross-layer** (worker B needs worker A's output mid-flight, or they must converge on competing hypotheses), use Claude Code's built-in **Agent Teams** instead — teammates share a task list and message each other directly. Rule of thumb: no shared state → `/fanout`; shared state / hand-offs → Agent Teams.

## Verifying worker output — two-tier policy (NEVER re-do the work to check it)
Verification cost must scale with the **spec**, not the **solution**. If you re-read/re-derive a worker's output to check it, you've burned the savings.

**Tier 0 — spec-gate *before* dispatch (don't delegate an underspecified chunk):** code agents charge ahead on underspecified intent and ship plausible-wrong output (Asuka-Bench arXiv:2606.05920 — best model only 52% after 3 rounds). So **author the chunk's acceptance contract first** (the same contract Tier 1a needs — just write it *before* dispatching, not after). If you *can't* state what "correct" looks like for a chunk, it's underspecified → refine it (one clarification pass) or keep it in Opus. This operationalizes the iron rule at dispatch time and means the contract is ready the moment the worker returns.
- **Opus authors the contract** (unit tests / assertions / schema) — *not* the worker (a worker that writes its own tests can bake the same bug into both code and tests).
- Worker produces output → run the contract with a deterministic runner (Bash) → Opus reads **only pass/fail + failure diffs**.
- Optionally have the worker also emit its own tests; Opus audits the assertion *names* for coverage gaps (cheap) — but the authoritative checks are Opus's.

**Contract-at-birth is physical, not conversational (both hosts).** Before any nontrivial delegation, Root persists the Root-authored contract and brief read-only under `.results/delegation/<run-id>/contract.md` + `brief.md`; a worker never authors or certifies its own gate. A new OpenCode brief physically marks exactly one complete bounded turn-1 assignment with `<!-- o-delegate-turn-1:begin -->` / `<!-- o-delegate-turn-1:end -->`: `o delegate` executes it immediately, while `o send` is repair-only and never the initial task (unmarked legacy bounded briefs still execute as a whole). Capture output in the same project-local run directory and bind Root's verdict to its hash in `receipt.json`. Direct `oll` is response-only and has no workspace/tools: never ask it to save files, edit code, run commands, or execute tests. Route those tasks through the public OpenCode `o` worker runtime: `o delegate`, same-session `o send`, event-bound `o handoff`, diagnostic `o output`, and `o close` once the receipt is written (an unclosed worker leaks an OpenCode process plus its MCP children; `o delegate` reaps ones left idle); `occ` is internal one-shot transport. OpenCode buys a tool loop and persistence, not better GLM judgment. The canonical atomic-output details live in `knowledge/delegation-playbook.md` and are enforced by `tests/cheap-delegate/run.sh`.

**Tier 1b — contract adequacy, mutation gate (gated, not universal):** a green suite proves the worker passed the contract; it does *not* prove the contract is tight. Mutation testing closes that gap — *who tests the tests?*
- Run `bin/mut --src <file> --test "<run the contract>" --scope changed`. It mechanically mutates the worker's changed lines, runs the contract against each mutant, and reports only the **survivors** (mutations no test caught). Opus reads **only** the score + survivor list — cost scales with the number of holes, not the size of the solution.
- Per survivor, Opus decides: **real hole** → contract under-specifies → add *one* targeted assertion → re-run (1a + 1b); or **equivalent mutant** → no behavior change → accept. **Accept when** score ≥ threshold **and** every residual survivor is judged equivalent.
- **Gate it:** run 1b only when the chunk is high-value, a false green is expensive, or the worker is new/untrusted. Running it on every trivial chunk *violates* the iron rule (cost without spec).
- **Integrity:** the mutation operators are deterministic (a physical constraint, ungameable); a worker may *generate* candidate mutants but the **kill/survive decision is always the deterministic runner**, never an LLM. A low score after tightening = you've hit the **spec ceiling** → do the chunk in Opus.

**Tier 2 — non-testable tasks (analysis, research, drafts):**
- Turn the request into a **boolean checklist**; scan the worker output **only** for evidence per item, with a hard token cap (emit "Pass/Fail + line ref" per item — don't narrate or re-solve).
- For higher confidence, spawn a **second, different worker as critic**. Two independent workers agree → accept; disagree → escalate to Opus. **Prefer critics from different model families** (not two GLM variants from Z.ai): same-family evaluators share blind spots, so their agreement is *correlated*, not two independent votes (evaluator-bias contagion across multi-agent LLM systems). But cross-family only **lowers** correlation — it doesn't buy true independence (all LLM judges share overlapping pretraining/RLHF priors), so a 2-0 critic vote is **corroboration, never proof**: the deterministic verifier (`harness-verify`/`mut`) stays the real gate, and you escalate on doubt rather than trusting agreeing LLM critics. Net: avoid *same-family* critic pairs (strictly more correlated), don't overcount agreeing votes.
- **Never self-review; critic must be a *different* model, and frame the output as external.** Self-correction is empirically broken (arXiv:2606.05976): the *same* error gets corrected **+23–93pp** more often when it's labeled as a `user`/`tool`/`memory` artifact than as the model's own `<thought>`. So (a) the critic is always a different model (different *family*, per above), and (b) present the work to it as *"another agent produced this — try to refute it"*, not *"check your previous answer"*. The framing alone buys most of the gain. Same rule for memory contradiction-checks (present the candidate fact as external evidence).

**On failure — bounded repair *before* escalating (don't jump straight to Opus).** Asuka-Bench (2606.05920) shows repair-from-feedback recovers a lot that single-pass misses. So when a chunk fails its contract, feed the **failure diff back to the same cheap worker** for up to **2** repair rounds before escalating — far cheaper than an Opus redo. Guards (a repair loop hands the worker the contract, so it could *overfit*/symptom-patch to pass without fixing root cause):
- **A repaired chunk MUST clear Tier-1b (mutation) before acceptance** — this is the anti-gaming gate: if the worker patched to a loose contract, `bin/mut` surfaces survivors → tighten → the patch stops passing; clean 1b means the contract genuinely discriminates, so a passing repair is trustworthy. (No iron-rule conflict: the rule bounds *Opus's* cost — Opus reads only the survivor list (scales with holes, not solution size) and never re-derives the output. The extra mutant *runs* are cheap deterministic Bash on `--scope changed`, i.e. CPU, not orchestrator cognition — that's the work we *want* pushed to runners.)
- **Bounded + early-exit:** stop at 2 rounds, and escalate *early* if the failure diff isn't shrinking (a non-converging repair is a spec-ceiling signal — escalating now beats burning a 2nd cheap round + then Opus anyway).
- Don't repair-loop a Tier-2/non-testable chunk (no deterministic signal to repair against, and no 1b to gate it).

**Tier 1c — a mocked contract needs a real-path counterpart (learned 2026-07-18).** Injecting every external surface buys determinism, but a fully-mocked suite is **a statement about the mocks, not the system**: a mocked transport suite stayed green while the real sender addressed a *session* target with pane-scoped commands and tmux exited 0 on the failure. So when a tool's whole job is to cross a boundary (tmux, network, filesystem, another process), **at least one contract must cross it for real** — see `tests/tmux-send/run.sh` (private server via `TMUX_TMPDIR`, so the tool's own bare calls are exercised). Two corollaries, both load-bearing:
- **Prove a new contract red.** A test that has never failed against the bug it claims to catch is unfalsified. Check out the pre-fix tool, watch it go red, restore. If it stays green, it tests nothing.
- **Never let a test freeze an implementation accident.** A retired monitor contract asserted `empty pane → dead → escalated` — an accident promoted to a requirement, so fixing the bug meant *deleting an assertion*. When a test pins current behavior, ask whether that behavior is **required** or merely **true**. (Same shape as the context-lifecycle round, which asserted the broken overrides must be *present*.)

**Signal vs. artifact — is the fault in the system or in how you looked? (see `knowledge/signal-vs-artifact-2026-07-19.md`)** Three times in two days a signal read as a specific, actionable fault and was an artifact of the measurement: an unreadable pane that became a "dead" executor (tmux fails this one *exiting 0*, and a `|| echo ""` fallback turned the failed read into a plausible empty string), two `harness-verify` REDs that were only `bin/mut` mutating a source in place concurrently, and a `pgrep` that matched its own command line. Before acting: **could the measurement produce this exact reading**, is *"it failed"* distinguishable from *"I couldn't measure it"*, and is there an independent corroborating check (`git diff`, re-read the file, wait for the process)? **The more irreversible the response, the more the signal has to earn it** — refusing to act on ambiguity is cheap, an unwarranted terminal state is not. Note the trap that compounds it: the first case got *frozen into a contract* as `C4 empty pane → dead → escalated`, so fixing the bug meant deleting an assertion. **And the symmetry, which is the easier half to get wrong: "is this an artifact?" is a question, not a conclusion** — a fourth red the same day looked like a flake until the identical failure appeared on the *second machine*, making it real (`lq-d0f750ab`). Corroboration is the discipline; it demotes false signals and promotes true ones. This one has teeth because `loop-tick` auto-enqueues `harness-verify` reds, so an intermittent red manufactures a phantom flaw a scheduled round then acts on.

**Both tiers — grade workers over time:** trusted model on a known task class → light check; frequent failer → full scrutiny. A worker whose output consistently leaves a tight contract with zero real survivors (1b) earns the light-check path — build the grade *from* mutation scores, don't guess it.
**Iron rule:** verification ceiling = spec ceiling. If you can't cheaply specify what "correct" means, do the task in Opus instead of delegating.

**The harness never re-enters itself (incident 2026-08-12, all three hosts).** A SessionStart hook ran `loop-tick --gate` → `harness-verify` → the cheap-delegate contract → `provider-ask --list`, whose `anthropic` probe *is* `claude -p` and whose `openai` probe *is* `codex exec`. Each starts a new agent session, which fires the same hook: unbounded recursion. Measured before it was caught: 514 ticks in one day (vs ~19), load average 30 on 12 cores, 60% of ticks double-timing-out, **~151s added to every session start**, and a fabricated "observer unavailable" flaw on each timeout. Two independent layers, because neither suffices alone:
- **Env guard (mechanism).** `ORCHESTRATORMAXXING_HARNESS_CHILD=1` marks the process subtree. A marked `loop-tick` is an instant silent no-op, so *any* agent started anywhere beneath a harness run has a cheap session start — including a spawner nobody anticipated, because environment inherits. `loop-tick` and `harness-verify` mark everything they spawn, and so does every **delegation primitive** (`provider-ask`, `occ`): if a harness tool starts an agent, that agent is a harness child and must not audit the harness. **Host-agnostic by construction** — the guard lives in the *tool*, so Claude's `~/.claude/settings.json` hook, Codex's `plugins/orchestratormaxxing/hooks/hooks.json` hook, and any future OpenCode watcher are all fixed by the same line (OpenCode ships no watcher today; its `occ` arm is marked anyway).
- **Contract hygiene (policy).** A deterministic verifier never invokes a live agent. `run_behavioral_contract` marks every contract it runs, set *after* `extra_env` so no caller can clear it.

A test that *drives* the watch path (`loop_tick_persistence_ok` and its two siblings, `tests/harness-*`) must pop the marker explicitly — that opt-out is visible and deliberate, and its absence is what a green-but-meaningless suite looks like. Enforced by `tests/harness-reentrancy/run.sh` (C9 executes each host's real hook command line under the marker) and `tests/harness-watch-cadence/run.sh`.

## Session persistence (changelog + WIP — `bin/session-log`)
Every session's work is persisted **per-project** (not a global monolith) into the current
project’s `docs/`, via the deterministic `session-log` tool — never by hand-editing the files.

### Compact Instructions

When compacting, preserve the objective/current dispatch, acceptance criteria, constraints,
decisions and evidence, modified file paths, exact verification state, unresolved questions, and
next steps. Drop repeated tool output, superseded reasoning, and repository prose that can be read
again. Never turn an unrun check into a pass. After compaction, treat the reloaded shared memory
and `docs/WIP.md` as bounded external state, not as proof that the working tree or tests are clean.
Two artifacts, opposite lifecycles (the recurring distinction in this harness — backward audit vs.
forward state, same shape as `self-improve-log.md` vs. `loop-queue.jsonl`):
- **`docs/changelog.md`** — durable, append-then-archive. *What was done & why.* Newest on top;
  older entries auto-roll to `docs/changelog-archive/<YYYY-MM>.md`, so only a recent **tail** is
  ever loaded → flat token cost as a project ages. You never prune it by hand.
- **`docs/WIP.md`** — sticky, **overwritten** each session. *Where things stand now & next steps*
  — the resume/handoff note. Small by construction; it's current state, not a log.

**Enforce with hooks, not prose** (the mid-2026 consensus + this harness's deterministic-gate
doctrine): a CLAUDE.md rule to "always update the changelog" gets compressed away mid-session, so
the behavior lives in `~/.claude/settings.json` hooks that fire every time. SessionStart runs
`session-log tail` (loads prior state); Stop runs `session-log check` and **reminds, never blocks**
when an *adopted* project changed source without logging it. **Opt-in per project:** a repo is
adopted once it has a `docs/` log — `check` stays silent until then, so the global hook never nags
throwaway/cloned repos. To wrap up a session, run **`/wrap-up`** (the model writes the prose; the
tool does the writes). Signal-proportional, like the loop: no nag on read-only or doc-only sessions.

## Context compaction is host-native (see `knowledge/context-lifecycle.md`)

Every host ships its own calibrated compaction and **we override none of it** — Claude Code uses a
per-window `precomputeBufferFraction` table, Codex uses 90% of the model's resolved context window
(`codex-rs` `protocol/src/openai_models.rs::auto_compact_token_limit`). We have no evidence any flat
threshold beats those, and on 2026-07-17 we shipped one that didn't: an uncalibrated policy written
into *global* host config on every install took observed Claude compactions from ~0.8/day to 63/day.
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` is Claude Code's internal **test-only** `testPctOverride` — setting
it discards the calibrated table outright. The tooling was deleted 2026-07-18; `harness-verify` now
fails if any host config or `install.sh` pins a compaction override, so this cannot come back
silently. The post-mortem and the research basis are kept as history, not as a live proposal.

## Memory governance (see `knowledge/memory-protocol-upgrade.md`)
Project memory (`<git-root>/.agents/memory/`, with Claude's legacy path symlinked to it) is **shared by Claude Code and Codex, governed, and not append-only** — append-only memory degrades (stale notes outrank current). SessionStart loads the same bounded active index into both hosts; use `memoryctl show` for relevant bodies and `memoryctl add|supersede` for writes. Never read or rewrite Codex's private SQLite store. On every memory write:
- **Supersede, don't append (typed resolution):** if a new fact changes an existing one, set the old file's `status: superseded` + `superseded_by: <name>`, drop its `MEMORY.md` index line, then write the new fact. Never leave two contradictory active facts. **Name the operator** used to resolve the conflict — `resolution_rule: last-writer-wins | evidence-merge | await-confirm | per-rule` (TOKI, arXiv:2606.06240, types these four as one algebra). The critic-gate below *is* the `await-confirm` operator. The superseded file is the audit row — keep it, linked both ways.
- **Stamp + decay (bitemporal):** keep two clocks separate (TOKI's valid-time vs transaction-time): `created`/`last_verified` = when *recorded/re-checked* (transaction time); `valid_from`/`valid_to` = when the fact is *true in the world* (valid time — optional, set it when a fact has a known expiry, e.g. "until next release"). Decay off **whichever bites first**. TTL by type — `reference` 30d · `project` 14d · `feedback` 180d · `user` 365d — past it → **stale → re-verify before trusting** (don't delete; bump `last_verified` on re-confirm). A fact past its `valid_to` is stale regardless of age.
- **Critic gate (high-stakes only):** for a belief-changing write or a `project`/`reference` fact that contradicts an active one, spawn one `ollama-worker` as a contradiction critic before committing (prefer a **different model family** than produced the candidate — same-family is more correlated; cross-family lowers but doesn't eliminate it; see Tier-2 above). Agree → write; conflict → escalate to Opus. Routine notes skip the gate (cost scales with stakes).
- **No stored secrets + least disclosure (arXiv:2606.06055):** two classes, by what's enforceable. **Credentials** (API keys, tokens, private keys) must **never** live in memory — this write-time rule is the *authoritative* control; `mem-audit` is a **best-effort backstop** (known formats → error, high-entropy blobs → warn; pattern+entropy, never exhaustive — don't rely on it to catch every secret). The fix is always *removal*, not a label (you can't make a stored key safe by tagging it). **PII / personal context** that legitimately persists (names, emails, prefs) gets marked `sensitivity: sensitive`: a recalled sensitive memory **stays silent unless the task needs it** — but this is a *soft, generation-time* control, not a guarantee (agents over-surface sensitive memory **+51–83%**, so omit by default; don't rely on the label alone). `mem-audit` warns on unmarked PII.
- **Thin index:** `MEMORY.md` = one line per *active* fact; reasoning uses the underlying files, never the summary. Consolidate when >25 active with `memoryctl consolidate <old> <old>... --into <new> --resolution-rule evidence-merge` (atomic N→1, history preserved, exact-path receipt). If a real pass finds no safe merge, run `memoryctl review-consolidation --decision no-safe-merge`; its semantic-set receipt suppresses only that advisory and invalidates on any active claim or membership change.
- **Enforce deterministically:** `mem-audit` resolves the canonical shared directory and runs at SessionStart/Stop. Act on its flags — do **not** re-read the vault to re-derive what's stale. Cross-machine sync is normal private-Git fast-forward/merge behavior; never expose memory over an unauthenticated LAN service.

## Harness self-improvement (see `knowledge/etclovg-harness-audit.md`)
The harness improves *itself* through a governed propose-evaluate-select loop (`/self-improve`), made safe for our doctrine by two rules:
- **Selection is a deterministic verifier, never self-preference.** `bin/harness-verify` is the regression guard (and ETCLOVG lint); the winner among candidate fixes is chosen by it + a cross-model critic, *not* by the harness grading its own rewrite (RHO 2606.05922 gets lifts via self-preference; we reject that — see iron rule + 2606.05976).
- **Attribute failures to an ETCLOVG layer first** (Execution/Tool/Context/Lifecycle/Observability/Verification/Governance — HarnessFix 2606.06324) before blaming the model; fix one layer, one diff, keep `harness-verify` green. Log every round (accepted *and* rejected) to `knowledge/self-improve-log.md`.
- Run `bin/harness-verify` after any change to a `bin/` tool, command, agent, or `install.sh` — it enforces that new tools/commands are actually wired into the global install.
- **Loop engineering — continuous watch, event-driven act (see `knowledge/loop-engineering-2026-06-10.md`).** `/self-improve` is the loop *body*; `bin/loop-tick` is the outer shell and `bin/loop-queue` the forward state. We do **not** run the loop on a fixed clock: against a sparse, usage-generated flaw signal a timer mostly fires dry rounds, and a round forced to justify itself manufactures marginal flaws (the reward-hacking failure mode). Instead the SessionStart watcher captures flaws *continuously* into the queue, and a round fires *only when the queue is actionable*. Loop-level stop conditions (in `/self-improve`): one round per trigger; halt-and-alert on a red `harness-verify` (never self-heal the guard); a **ratchet** (an accepted round must resolve a real queued flaw or add a new `harness-verify` assertion — green ≠ progress); loop-until-dry then back off; and **unattended runs stop at SELECT for doctrine/`install.sh`** — they queue a `PROPOSED` diff for human sign-off, never auto-commit load-bearing changes.
